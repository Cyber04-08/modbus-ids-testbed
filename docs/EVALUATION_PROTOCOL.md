# Evaluation Protocol

What "normal traffic" means, how attacks are labeled, which capture session is
used for what, and what the overhead measurements do and do not claim. Written
on 2026-10-05 in response to instructor feedback on Assignments 01 and 02.

## 1. Normal (benign) traffic

Normal traffic is generated by `testbed/hmi_client.py`, a simulated operator
on its own TCP connection to the PLC (through the passive tap). It is the only
benign client in every session.

| Property | Definition |
|---|---|
| Process | Water tank: HR0 = tank level (sensor, read-only), HR1 = pump setpoint (%), coil 0 = inlet valve, coil 1 = outlet valve |
| Poll | Every cycle: FC3 read of HR0 (count 1) |
| Cycle time | 1.0 s nominal, uniformly jittered by +/- 0.25 s |
| Setpoint change | Per cycle, probability 0.20: FC6 write to HR1, previous value +/- 5 or 10, clamped to 20-90 % (starts at 40) |
| Inlet valve | Per cycle, probability 0.10: FC5 toggle of coil 0 |
| Outlet valve | Per cycle, probability 0.08: FC5 toggle of coil 1 |
| Function codes used | FC3 (read holding registers), FC6 (write single register), FC5 (write single coil) only |
| Never does | Write to HR0, use FC16, write a setpoint outside 20-90, reuse a transaction ID |
| Transaction IDs | Strictly increasing per request (pymodbus client) |

Measured on the training session (`data/baseline_capture.csv`, 60 s): 90
requests, of which 58 FC3 reads, 17 FC6 setpoint writes and 15 FC5 valve
writes.

Known limitation: real plant traffic is more varied than this (more devices,
operator shifts, maintenance events), so the false-positive rates measured here
are likely optimistic for the ML detector and the rule set is specific to this
process.

## 2. Attack labels (per packet, from the attack scripts' own logs)

1. Each attack script opens its own TCP connection and reports its ephemeral
   source port (`SOURCE_PORT=<n>`), so every packet on that connection can be
   attributed to it.
2. Each attack script also logs every request it sends (`PACKET=<json>`:
   exact frame bytes, transaction ID, kind, description). The orchestrator
   (`attacks/run_scenario.py`) stores these in `data/attack_manifest.json`.
3. `data/label_dataset.py` matches every captured request on an attack
   connection, in order and by exact bytes, to its logged record, and reports
   the match rate (expected: 15/15 per session). The attack's wall-clock
   window is checked as an independent cross-check. Timestamps alone are never
   used to assign a label.

| Label | Meaning | Scored? |
|---|---|---|
| `benign` | Request from the operator's connection | yes, `is_attack=0` |
| `replay` | One of the 8 verbatim retransmissions of the captured write (reused transaction ID) | yes, `is_attack=1` |
| `injection` | One of the 6 fabricated unauthorized writes | yes, `is_attack=1` |
| `replay_seed` | The replay script's first send of the frame, its stand-in for the operator command an attacker would have recorded. Not itself a replay | no |
| `response` | A reply generated by the PLC. Responses are never client requests, so they are never labeled malicious, even on an attacker's connection | no |

Unscored rows stay in the traffic stream the detectors see (the replay rule
must see the seed to recognize the repeats); they are only left out of the
metrics. Each test session therefore has 14 scored attack requests.

## 3. Capture sessions (train / tune / test)

Every session is a separate process run of the whole testbed (fresh PLC, tap
and operator, fresh random timings and setpoints). No session's data is reused
for another role.

| Role | Produced by | File | Used for |
|---|---|---|---|
| Train | `testbed/capture_baseline.py` | `data/baseline_capture.csv` | Fitting the Isolation Forest (normal traffic only) |
| Tune | `attacks/capture_tuning.py` | `data/tuning_labeled.csv` | Choosing the ML contamination (its attack fraction) and, for the tuned ML detector and the one-class SVM, the alert threshold (best F1 on this session) |
| Test (x10) | `detectors/multi_run.py` (scenario + labeler per run) | `data/runs/run_XX.csv` | Final scoring only |

The rule-based detector has no trained or tuned parameters: its rules come
from the plant's register map, fixed before any data was captured.

Before this protocol (results in `data/v1_before_feedback/`), the ML
contamination was set from each test session's own attack fraction, i.e. from
test labels. Measured effect of that leak, scoring the same 10 new test
sessions both ways:

| ML contamination taken from | precision | recall | FPR |
|---|---|---|---|
| each test session's own labels (old, leaky) | 0.507 | 0.900 | 0.203 |
| the separate tuning session (current, 0.177) | 0.531 | 0.871 | 0.182 |

The leak made the ML detector look slightly better at catching attacks; it
also shows the ML result is sensitive to this one setting, which is why
threshold selection was the first second-half work item (2026-10-15):
the tuned ML detector sets its alert threshold at the best F1 on the
tuning session instead, see `docs/SETUP_LOG.md`. The rule-based detector is
unaffected (it has no tuned parameters).

Limitation: every session runs the same attack sequence; only the benign
traffic varies between sessions. Varied and harder attacks are planned.

Enforced since 2026-10-20: `evaluate.py` and `multi_run.py` abort if any two
of the train / tune / test sessions share a captured request (the tuning
session is saved by copying `labeled.csv`, so the old defaults could score it
against itself), and the capture scripts move an existing session file to
`data/backups/` instead of overwriting it. `multi_run.py` records the SHA-256
of every input file in `data/multi_run_provenance.json`.

How results are stated: because every test session replays the same attack
script, a detector that misses one fixed packet misses it in every run, so
the over-runs confidence interval is exactly 0 and says only that the runs
agree. Rates are therefore also given as pooled counts with a Wilson 95%
interval, e.g. OC-SVM: 0 false alarms in 610 benign requests (true rate
0-0.6%), recall 130/140 (0.87-0.96).

Design choices tuned against the saved test runs: the transaction-ID-change
feature, the first-gap fill and the one-class SVM's `nu` were chosen while
scoring the same 10 saved runs (the tuning session decides thresholds, but
these design decisions were compared on test results). The planned harder
attacks will be scored once, as an untouched final test.

## 4. What the overhead numbers claim

The detectors analyze a recorded copy of the traffic. They are not in the
request path between the operator and the PLC, so they add no delay to the
control cycle by construction (the equivalent deployment is a monitoring host
on a mirrored switch port). The reported time and memory are therefore the
**detector's processing cost on the monitoring host**: how much computing a
plant would need to dedicate to running it. They are not, and are not claimed
to be, a measurement of control-loop delay. The passive tap is test
instrumentation for capturing traffic on one machine, not part of either
detector.

## 5. Generalization check (does a detector work when the attack changes?)

Section 3's limitation - every tuning and test session ran the same attack
script - means a threshold tuned at best F1 on the tuning session may have
been fitted to the one attack sequence it is later tested on. Three steps
measure this (`detectors/generalization.py`):

1. **Varied attacks.** `attacks/run_scenario.py --vary [--seed N]` draws, per
   session, the attack order, the baseline padding, and a seed for each attack
   script; the scripts then draw their own frames, counts and timing (replay:
   which write is replayed, how many copies, 0.3-1.5 s apart; injection: 3-8
   commands from the same kinds plus an in-band setpoint the fixed sequence
   never sent). Every drawn value is recorded in the run's manifest, so a
   varied session reproduces exactly. Without `--vary` the scripts send the
   original bytes, so the Section 3 results still reproduce.
2. **Three ways to set the ML alert threshold**, compared on the same runs:
   tuned at best F1 on the fixed tuning session (the Section 3 protocol);
   tuned on a separate varied session; and **label-free** - the score above
   which at most 0.5 % of a separate normal-only session alerts, using no
   attack labels at all (`ml_anomaly.normal_quantile_threshold`).
3. **Leave-one-attack-type-out** and **threshold-free** quality: tune on one
   attack type and grade on the other; and ROC AUC / PR AUC of each ML score,
   so a result does not hinge on one threshold.

Headline finding (10 varied runs, train 90 benign): the one-class SVM's
separation is intact (ROC AUC and PR AUC 1.000 on varied as on fixed attacks),
so its detection power was not an artifact of a repeated attack. What was
fragile is threshold selection: a best-F1 threshold overfits the tuning
attack, while the **label-free threshold gives F1 0.993 (recall 1.000, FPR
0.4 %)** on varied attacks with no labels to overfit. The Isolation Forest's
earlier numbers were optimistic (varied F1 ~0.58; recall 0 under the
label-free threshold). The label-free threshold is therefore adopted as the
one-class SVM's reported selection method.

## 6. Harder attacks and countermeasures (limitations 1 and 2)

Two attacks are built to defeat the signals the detectors relied on, run from
two attacker origins, and scored once as a final test
(`attacks/harder_scenario.py`, `detectors/harder_attacks.py`):

| Attack | Defeats | How |
|---|---|---|
| `txid_replay.py` | reused-transaction-ID signal (rule `replay_reused_txid`, feature `txid_delta`) | resends one captured command with fresh, incrementing transaction IDs, paced like the operator (cover polls + write 1-5 ms later) |
| `mimic_injection.py` | timing separation and value-range checks | injects in-band writes (setpoint 20-90 %, valves ON/OFF) 1-5 ms after its own cover polls |

| Origin | Attacker source IP | Meaning |
|---|---|---|
| `separate` | 127.0.0.66 | a distinct host on the ICS LAN |
| `spoof` | 127.0.0.1 | the operator's own address (co-located or spoofed) |

Countermeasures added (off by default, so Sections 3 and 5 are unchanged):

- **Sender identity** (rule `unknown_source`): flag a write from a host that
  sent no traffic in the normal training session. `RuleBasedDetector(
  known_sources=...)`.
- **Value-change features** `repeat_run` (identical writes in a row to one
  target) and `write_step` (step from the last value written), added to the
  one-class SVM as `OCSVM_CONTEXT_FEATURE_COLUMNS` ("ocsvm-ctx"). A replay that
  rewrites its transaction IDs still repeats the same command, which
  `repeat_run` sees.

Cover polls carry the label `cover` and are left unscored (they change nothing
in the process). Results and the regression check (that the value-change
features do not weaken the Section 5 varied-run result) are written to
`data/harder/`. The honest boundary this exposes: a timing-mimicking, in-band
injection sent from the operator's own address is not caught by any passive
content/behaviour method here - only sender identity catches it, and only when
the attacker is on a different host. That is the case Modbus/TCP authentication
(Modbus/TCP Security, TLS with role-based authorization) exists to close, and
it is stated as such rather than papered over.

## 7. Authentication as the closing control (`testbed/secure_modbus.py`)

Section 6 ends on a case no passive method here catches. This section measures
the control that does. `secure_modbus.py` wraps each request in an envelope
(8-byte counter, the frame, a 16-byte HMAC-SHA256 tag over both); a gateway
accepts it only if the tag verifies and the counter is higher than any accepted
before. It stands in for Modbus/TCP Security (TLS); it reproduces integrity and
anti-replay, not confidentiality or certificates, so its cost is a lower bound.

`detectors/auth_eval.py` pushes the saved harder and varied sessions through
the gateway (operator sealed in order; attacker per capability):

| Attacker capability | Replay blocked | Injection blocked | Operator wrongly blocked |
|---|---|---|---|
| no key (made-up tag) | 100 % | 100 % | 0 % |
| resends a sniffed envelope | 100 % | 100 % | 0 % |
| reuses a sniffed tag on a changed frame (rewritten txid/value) | 100 % | 100 % | 0 % |
| holds the key | 0 % | 0 % | 0 % |

(Same result on `harder/separate`, `harder/spoof` and `varied`; 10 sessions
each; the mimic injection from the operator's own address is blocked too,
because the check is on a secret, not on timing, values or address.)
Cost: about 4 us to seal and 4 us to verify per request (rule-based detector
0.0027 ms, one-class SVM 0.034 ms), plus 24 bytes on a 12-byte frame.

What this does and does not show: it is a protocol property demonstrated on
the project's traffic, not a discovery; the keyless result is expected by
construction. The useful findings are the cost beside the detectors and the
boundary: with a stolen key authentication is blind (a detector still has a
chance there), so the two are complementary. Key distribution, rotation and a
constrained-device budget are out of scope. Outputs: `data/auth_results.csv`,
`data/auth_cost.csv` (gitignored).
